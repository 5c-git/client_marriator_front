## Постановка

*(текст с портала, 27–28.10.2026)*

**ЦЕЛЬ ЗАДАЧИ:**
Убрать страницу ошибки, которую видит пользователь после успешного сохранения услуги (баг №1.1 Прогона #1, TC-2001, видео 1:10). Родительская задача: #88945.

**КАК РАБОТАЕТ СЕЙЧАС:**
Данные сохраняются, но пользователю показывается страница ошибки 422. В отчёте Прогона #1 текст ошибки «The order id field must be an integer» (страница /orders/1015).

**ЧТО УСТАНОВЛЕНО (проверка Владимира Кормишина 27.10.2026, DevTools → Network):**
Последовательность запросов при сохранении услуги в Задаче:

1. updateTaskActivity — 200, данные сохранены на сервере.
2. getData — 200, данные получены успешно.
3. getTask?taskId=new-task — 422. В параметр taskId попадает слово «new-task», а не число. Бэкенд отвечает верно: правило taskId — целое число, существующая задача.

Скриншоты: https://skr.sh/seByY9lC7ef и https://skr.sh/seBK1sgww4l

Условие воспроизведения: ошибка возникает только если услугу создали в новой Задаче и сразу открыли её на редактирование, не выходя со страницы. Если выйти в общий список задач, заново открыть задачу, открыть услугу и сохранить, запрос уходит как getTask?taskId=950 (реальный id) и ошибки нет.

Вывод: проблема не на бэкенде. После создания новой Задачи адрес/состояние страницы остаётся со значением «new-task», и оно подставляется в запрос как идентификатор. Вероятно, дело в маршрутизации или в состоянии, которое не обновляется после создания.

**ПРИЧИНА НАЙДЕНА В КОДЕ ФРОНТА (28.10.2026):**
Файл `app/routes/activity/activity.tsx`, action, ветка updateService при isNew (около строк 158-161): редирект идёт на `/tasks/new-task?taskId=950`. Такой адрес не совпадает с маршрутом `new-task/:taskId` (`app/routes.ts:25`), а совпадает с маршрутом `:lang?/tasks/:taskId` (task.tsx). В итоге taskId = «new-task», и загрузчик вызывает `getTask("new-task")` → 422. Ветка createService (около строки 152) редиректит верно: `/tasks/new-task/950`.
Для Поручения то же: `/orders/new-order?orderId=1015` попадает в `:orderId`, `getOrder("new-order")` → «The order id field must be an integer» (это ошибка из отчёта Прогона #1).

**ЧТО НУЖНО СДЕЛАТЬ:**

1. В ветке updateService при isNew редиректить как в createService: `/<plural>/<new>/<entityId>` вместо `/<plural>/<new>?<entity>=<entityId>`.
2. Проверить, что для Задачи и для Поручения после сохранения услуги открывается страница `new-task/:taskId` и `new-order/:orderId` с реальным id.

**КРИТЕРИИ ПРИЕМКИ:**

1. В новой Задаче создать услугу, сразу открыть её на редактирование и сохранить: страница ошибки не показывается, запросов getTask с нечисловым taskId нет.
2. Те же действия для Поручения: запросов с нечисловым orderId нет.
3. Повторный прогон TC-2001 (qadesk run 361) проходит этот шаг.
4. В комментарии к задаче описано, зачем вызывается второй запрос и откуда бралось неверное значение.

## Вопросы к постановщику

*(сгенерированы шагом 5.5 `task-start` 2026-10-28, ответы постановщика — там же)*

1. Что делать, если после сохранения реальный taskId/orderId не получен или пуст — куда редиректить и что показывать пользователю?
   **Ответ:** редиректить на список Задач; у Поручений, если такое поведение воспроизводимо, — на список Поручений.
   *Проверка в коде (28.10.2026):* ветка `updateService` в `activity.tsx` одна на обе сущности (словарь `vocabulary` переключает `tasks`/`orders`); ошибка Поручения из Прогона #1 (страница `/orders/1015`, «The order id field must be an integer») идёт из этого же места. Fallback «пустой/нечисловой entityId → список сущности» в общем коде покроет Задачи и Поручения одним местом.
2. Каким должно быть поведение при повторном сохранении той же услуги (двойной сабмит / повторный вызов action)?
   **Ответ:** не решать в рамках этой задачи. Двойной сабмит просто выполняет те же действия, что и одинарный: сохранить и редиректнуть. (Предотвращение двойного сабмита — кандидат в отдельную задачу.)
3. Каково ожидаемое поведение, если ту же услугу в той же новой Задаче одновременно редактируют в двух вкладках или два пользователя?
   **Ответ:** сохраняются значения, пришедшие последними; отдельных мер не требуется.
4. Должна ли страница `new-task/:taskId` / `new-order/:orderId` ограничивать открытие по чужому реальному id?
   *(исходная формулировка была непонятна постановщику; переформулирована)* Вопрос: если пользователь подставит в адрес id чужой Задачи/Поручения — кто решает, показывать ли её?
   **Ответ:** права разбирает сервер. Если выполнился запрос по чужой задаче — сервер откажет с соответствующей ошибкой; фронт ничего дополнительно не делает.
5. Что делать при частичном отказе: updateTaskActivity вернул 200, но getData или последующий getTask упал — редирект всё равно выполняется?
   **Ответ:** при сетевых ошибках предусмотрен механизм показа ошибки; в рамках текущей задачи об этом не беспокоиться.
6. Нужна ли компенсация, если после успешного сохранения загрузка страницы по новому адресу завершается ошибкой?
   **Ответ:** ничего; ошибки обрабатывает готовый механизм.
7. Что показывать, если права на Задачу/Поручение отозваны между сохранением услуги и открытием страницы по реальному id?
   **Ответ:** на фронте ничего дополнительного не делать: ошибку при сохранении вернёт сервер, фронт покажет её механизмом обработки ошибок. Правок не требуется.
