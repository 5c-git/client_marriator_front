## Д-1. Пояс глобальных настроек intervalDayStart/End

- **Что неоднозначно:** постановка (п.2) требует «определить, в каком поясе хранятся глобальные настройки, и привести к одному правилу; если неясно — вернуть вопрос Владимиру».
- **Что определил (28.10.2026, по исходникам бэкенда):** настройки хранятся как строки БЕЗ конвертации таймзоны: в базе `intervalDayStart='9:00'`, `intervalDayEnd='21:00'` (миграция 2025_12_28_343534_add_interval.php, дамп dev_marriator.sql), getFromKey и админ-сохранение отдают/пишут значение как есть — в отличие от рабочих часов проекта, где админка вычитает/добавляет 3 часа (ProjectController.php:45-46, 65-66). То есть настройки — «локальные по смыслу» строки, часы проекта — UTC.
- **Что выбрал:** правило эталона activity.tsx:103-110 — fallback из intervalDayStart/End собирается тем же шаблоном `2026-03-12T${value}:00Z`, без проверки ведущего нуля. Приведение к одному правилу = правило эталона (директива «повторить готовое»).
- **Известная цена выбора:** на реальном значении `'9:00'` (час без ведущего нуля) шаблон даёт Invalid Date — и даёт его одинаково в эталоне activity.tsx и теперь в Заявке. Прежний код bid.service.ts дополнял нулём только start (и именно эта проверка портила «21:00» → «021:00» в bid.tsx). Fallback срабатывает только когда у проекта не заданы рабочие часы.
- **Почему:** директива постановщика «повторить готовое, функционал не расширять»; эталон с этим правилом в проде; расхождение хранится в OPEN_QUESTIONS №1.
- **Что сломается, если выбор неверен:** запасная рамка (проект без рабочих часов) не сдвинется, а развалится (NaN-часы → проверки молчат) — симптоматика идентична эталону, т.е. регрессии относительно Задачи нет, есть унаследованный дефект контракта.
- **Риск:** обычный
- **Затронуто:** `app/routes/bids/bid/bid.service.ts:46-58`
